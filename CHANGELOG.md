## [Unreleased]

## [2.1.0] - 2026-11-11

First release published to npm. Version 2.0.0 existed only in this repository and was never published; 2.1.0 aligns the package with the other `@romatech/orm-providers-*` 2.1.0 releases. It requires `@romatech/orm` `^2.0.0`.

### Added
- SQLite via sql.js (WASM, zero native dependencies), for Node.js.
- CRUD, unit of work (`saveChanges`), queries, migration history, scaffold.
- Transactions through `DbContext.beginTransaction()` (raw `BEGIN`/`COMMIT`/`ROLLBACK`).
- Composite primary keys in `createTable` (every column flagged `primaryKey`).
- Type mapping: `boolean` → `BOOLEAN` (stored as 0/1), `Date` → `DATETIME` (ISO-8601 text); entity reads convert them back to `boolean` and `Date` by declared column type.
- README sections on persistence (in-memory database written back to the file), single-writer use, type mapping and primary keys.

### Security
- **SQL injection through identifiers** (fixed before first publication): table and column names were wrapped in quotes without escaping, so an entity key such as `x"=1, "tenant"=? WHERE "id"=? OR 1=1 --` rewrote an `UPDATE` to change every row. Identifiers are escaped and all values are bound as parameters.

### Fixed (relative to the unpublished 2.0.0 source)
- `executeQuery(QueryObject)` ignored `where`/`orderBy`/`skip`/`take`/`select` and returned the whole table. It now pushes `WHERE`/`ORDER BY` to SQLite and applies the rest (and any predicate that could not be translated) in memory.
- Booleans (stored as 0/1) and dates (stored as ISO text) were compared as stored by the in-memory re-evaluation, so `where(x => x.active === true)` and `where(x => x.born > date)` silently returned no rows. Values are now converted by declared column type before the re-evaluation.
- `createTable` with several `primaryKey` columns failed (`more than one primary key`); an interim fix kept only the first column, a weaker key than intended. All flagged columns now form the key, and an explicit `primaryKey` that is missing from the columns or contradicts the flags is rejected with a clear error.
- `update`/`remove`/`find` assumed an `id` column; they use the table's primary key and reject tables with a composite key instead of matching several rows.
- A failing `saveChanges` left `BEGIN` open and every later call failed; `saveChanges` inside `DbContext.beginTransaction()` failed with a nested `BEGIN`. Each batch now runs in a savepoint and is rolled back as a whole on failure.
- `Date` and `undefined` values made sql.js throw (`Wrong API use`); dates are stored as ISO-8601 text and `undefined` properties are skipped (or bound as `NULL`).
- The file passed as connection string was read but never saved. The database file is written atomically (temporary file + rename) after each successful `saveChanges`, each DDL statement, each migration-history change, each raw write outside a transaction and each `COMMIT`; nothing is written while a transaction is open, and `disconnect()` with an open transaction discards it.
- `PRAGMA foreign_keys = ON` is restored after each file write (sql.js reopens the database on export). The `PRAGMA journal_mode = WAL` call and the README "WAL" claim were removed: they do not apply to sql.js.

### Known issues
- `WHERE` clauses are generated by `@romatech/orm`. With `@romatech/orm` 2.0.x, `where(x => x.name !== 'a')` and `where(x => !x.flag)` become `"name" != ?` and `"flag" = ?`, which silently drop rows where the column is `NULL` (JavaScript keeps them). Use `@romatech/orm` 2.1.0 or later, which generates NULL-aware SQL.

### Build / CI
- `package-lock.json` re-synced with `package.json` (it pinned `@romatech/orm@1.2.0`, so `npm ci` failed).
- CI runs `npm ci`, build, tests, `npm audit --omit=dev` and `npm pack --dry-run` on Node 22 and 24, with read-only `contents` permission.
- The publish workflow installs with `npm ci` on Node 22 and no longer rewrites the `@romatech/orm` range in `package.json` at publish time.
- Added `npm test` (Node test runner, runs against `dist/`, so build first).
